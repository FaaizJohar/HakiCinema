* Server-side rendering or static generation for public discovery pages.

## 3.2 Indexing rules

Create an explicit indexing policy for every page type.

Potentially indexable pages, if they contain substantial original value:

* Homepage.
* Anime catalog.
* Genre landing pages.
* Useful seasonal anime collections.
* Individual anime information pages.
* Legitimate episode guides.
* Editorial recommendations.
* About, contact, privacy, and terms pages.

Potentially non-indexable pages:

* Internal search result combinations with little unique value.
* Empty categories.
* Duplicate sorting and filter combinations.
* Account pages.
* Private watchlists.
* Temporary playback sessions.
* Internal API endpoints.
* Tracking and utility URLs.

Choose `index`, `noindex`, canonicalization, and access restrictions deliberately.

Do not automatically index every URL generated by the application.

## 3.3 URL architecture

Use descriptive, stable, readable URLs.

Example architecture:

* `/`
* `/anime/`

Requirements:

* One preferred hostname.
* Consistent HTTPS.
* One canonical URL format.
* Correct trailing-slash policy.
* No unnecessary tracking parameters in canonical URLs.
* No duplicate paths created by case differences.
* No arbitrary URL changes without a redirect plan.
* No fabricated pages created solely to target keywords.

* `WebPage`
* `BreadcrumbList`
* `Article` or `BlogPosting` for genuine editorial articles.
* `Person` for actual credited individuals where appropriate.

Do not add fake ratings, invented reviews, misleading availability, nonexistent video metadata, or fabricated episode information.

Do not assume that Anime-specific structured data automatically generates a special Google search appearance.

# PHASE 10 — CORE WEB VITALS AND PERFORMANCE

Optimize actual user experience rather than pursuing a perfect-looking synthetic score.

Audit and improve:

* Largest Contentful Paint (LCP).
* Interaction to Next Paint (INP).
* Cumulative Layout Shift (CLS).
* JavaScript execution time.
* Main-thread blocking.
* Image size and format.
* Font loading.
* Caching.
* Compression.
* Route-level code splitting.
* Unnecessary dependencies.
* API response times.
* Layout stability during loading.

Targets for good Core Web Vitals at the 75th percentile:

* LCP: 2.5 seconds or less.
* INP: 200 milliseconds or less.
* CLS: 0.1 or less.

Use properly sized WebP or AVIF images where suitable, responsive image sources, explicit image dimensions, and lazy loading for off-screen content.

Do not lazy-load the primary above-the-fold image if doing so harms LCP.

Use a CDN and cache static assets when compatible with the existing hosting architecture.

Preserve streaming and playback reliability. Never cache private account data or protected media in a way that exposes it to other users.

Run Lighthouse and real-world performance checks before and after implementation. Distinguish laboratory results from field data.
